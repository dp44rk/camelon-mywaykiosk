# 성능 평가

> 상태 (2026-10-30): **연동 모드 주문 완료·화면 변환(규칙·AI)·쉬운 말 지표는 측정 완료**. **카메라 모드(비전 모델)는 측정하지 못했다** — Air API의 Qwen3.8-27B 엔드포인트가 그림이 들어간 요청을 모두 `400 Invalid request`로 거부한다(글만 보내면 정상 응답). 평가 세트 276장과 도구(`eval/run.mjs`)는 준비되어 있어 엔드포인트가 그림을 받으면 바로 잰다.

## 1. 평가 세트

`node eval/capture.mjs` 가 만든다 (서버를 `MOCK_AI=1`로 켠 상태).

- 목업 카페·식당 키오스크를 **주문 목표 5개**로 처음부터 주문 번호까지 실제로 눌러 가며 화면 **69장**을 찍는다.
  - 목표: 차가운 아메리카노 포장 / 따뜻한 카페라떼 매장 / 레몬에이드 포장(다른 분류 탭에 있음) / 김치찌개 매장 / 물냉면 포장(면류 탭)
  - 화면 종류: 시작, 매장·포장, 앱 광고 팝업, 메뉴, 옵션, 세트·추가 권유, 주문 확인, 적립, 결제 수단, 카드 투입, 완료
- **정답**: 그 화면에서 눌러야 하는 버튼 상자. 연동 엔진이 고른 버튼이며, 이 버튼만 눌러 5개 목표 모두 주문 완료까지 가는 것을 확인했다.
- **사진처럼 변형** 4가지 (정답 상자 좌표도 같이 변환):
  - `clean` 화면 캡처 그대로
  - `photo` 키오스크 몸체·배경, −4° 기울기, 약한 흐림
  - `tilt` +7° 기울기, 흐림, 빛 반사
  - `dim` 어둡게(밝기 55%), 강한 흐림
- 합계 **276장**. 사진 파일은 다시 만들 수 있어 git에서 뺐고(`eval/images/`), 정답 목록 `eval/set.json`만 올린다.
- 한계: 진짜 폰 카메라 사진이 아니다. 반사·모아레·손떨림은 흉내만 냈다. 실제 매장 키오스크 사진으로 검증하는 것은 남은 과제다.
  - huddling.ai 키오스크 스크린샷 모음은 "All rights reserved" 표기라 쓰지 않았다(이 세션에서는 접속도 막혀 있었다).

## 2. 화면 변환 성공률 (원제안자 답변: "화면 변환의 성공률이 더 중요")

`node eval/convert-metrics.mjs [--ai]` → `eval/results/convert-<rule|ai>.json`

키오스크 화면 구조(버튼 글자·종류·위치·묶음 제목)를 "내 방식 화면" 설계로 바꾼다. 설계에는 쉬운 말 라벨, 묶음, 순서, 짧은 설명이 들어간다.
- **성공**: 모든 버튼이 정확히 한 번 나온다(빠짐·지어냄·중복 0). 그리고 모든 라벨이 검증기를 고치지 않고 그대로 통과한다.
- 변환된 화면의 버튼을 누르면 원래 화면의 버튼이 눌린 것과 같다. 그래서 기존 결제 흐름이 그대로 이어진다.

| 지표 | 규칙 변환 | AI 변환 (DeepSeek-V4.1-Flash) |
|---|---|---|
| 화면 수 / 버튼 수 | 69 / 389 | 69 / 389 |
| 변환 성공률 (고침 없이 통과) | 100% | **73.9%** (51 / 69) |
| 버튼 보존율 | 100% | **100%** |
| 지어낸 버튼 | 0 | **0** |
| 검증기가 바꾼 라벨 | 0 | 31개 (18화면) |
| 어려운 말 라벨 (변환 전 → 검증 후, 메뉴 이름 제외) | 178 → 0 | 178 → 0 |
| AI 실패로 규칙에 기댄 화면 | — | 0 |
| 응답 시간 중앙값 / 90% | 0초 (즉시) | 2.7초 / 4.3초 |

측정: 2026-10-30, `node eval/convert-metrics.mjs --ai` → `eval/results/convert-ai.json`.

화면 종류별 AI 변환 성공 (고침 없이 통과 / 화면 수): 시작 5/5 · 광고 5/5 · 권유 5/5 · 주문 확인 10/10 · 완료 5/5 · 매장·포장 4/5 · 메뉴 9/12 · 적립 3/5 · 결제 수단 2/5 · 카드 투입 1/5 · **옵션 2/7 (고친 라벨 16개)**.

- AI는 버튼을 하나도 빠뜨리거나 지어내지 않았다. 실패한 18화면은 모두 **라벨에 사전 기준 어려운 말이 남아** 검증기가 규칙 라벨로 바꾼 경우다. 그래서 사용자에게 보이는 최종 화면의 어려운 말은 0이다.
- 옵션 화면(HOT/ICE, Regular/Large, 샷·시럽)에서 가장 많이 고쳤다. 다음 개선: 프롬프트에 사전의 바꿀 말 목록을 넣거나, 검증기가 고친 예를 되먹이기.
- 검사 사전이 규칙 변환과 같다는 한계는 그대로다. AI 라벨이 사전 밖의 다른 쉬운 말을 써도 '어려운 말'로 잡히지는 않지만, 사전 안의 말을 그대로 두면 잡힌다.

- 규칙 변환은 같은 사전으로 만들고 같은 사전으로 검사하므로 100%가 나오는 게 당연하다. 이 숫자는 **바닥선(fallback)이 항상 온전하다**는 뜻으로만 읽어야 한다.
- AI 변환에서 볼 것은 두 가지다. 묶음 이름·설명이 더 자연스러운지, 그리고 검증기가 몇 번 고쳤는지(`relabeledByValidator`, `invented`)다.
- 실제 동작에서는 규칙 변환을 먼저 그려 지연을 없앤다. AI 결과가 오면 바꾸고, 같은 화면은 저장해 다시 쓴다(답변서의 "케이스별 화면 저장").

## 4. 쉬운 말 지표

`node eval/plain-metrics.mjs` → `eval/results/plain.json`

69개 화면에서 **키오스크 화면에 보이는 버튼 글자**(원문)와 **내 방식 QR 안내 문장**을 비교했다.

| 지표 | 키오스크 원문 | 안내: 처음 사용 | 안내: 가끔 | 안내: 자주 |
|---|---|---|---|---|
| 어려운 말 (100어절당) | **29.2** | **0** | 0 | 0 |
| 한 화면에서 받는 선택지 수 | 평균 8.1개 | **할 일 0.93개** | 0.93 | 0.93 |
| 문장당 어절 수 (평균 / 최대) | – | 3.6 / 6 | 3.6 / 6 | 4.9 / 8 |
| 검사기 통과율 | – | 100% | 100% | 100% |

해석과 한계:

- "어려운 말 0"은 **같은 사전으로 만들고 같은 사전으로 검사**한 결과라서, 원래부터 0이 나오게 되어 있다. 사전 밖의 어려운 말이 없다는 증명이 아니다.
- 화면에 쓰인 글자('테이크 아웃' 같은 것)는 사용자가 화면에서 찾아야 하므로 **일부러 그대로 읽고** 뒤에 뜻("가지고 가기라는 뜻이에요")을 붙인다. 이 따옴표 안의 글자는 지표에서 뺐다.
- 진짜 검증은 **어르신 사용자 시험**이다: 주문 성공률, 걸린 시간, 도움 요청 횟수, 안내 문장을 듣고 맞게 누른 비율. 아직 하지 않았다.

비교할 모델: Qwen3.8-27B(이미지·영상), Qwen3.5-9B(이미지 1장, 더 빠름).

**측정하지 못한 이유 (2026-10-29~30)**: `node scripts/probe-vision.mjs`로 요청 모양을 하나씩 시험했다. 같은 엔드포인트에 글만 보내면 200으로 답한다. Air API 문서의 예시 그대로(`content` 배열 + `image_url.url`) https 그림, 64px PNG, 키오스크 JPEG를 보내면 모두 `400 Invalid request`가 난다. 형식을 일부러 틀리면 다른 오류(JSON 해석 실패)가 나므로, 요청은 해석된 뒤 그림 때문에 거부되는 것이다. `eval/run.mjs --limit 20`(80장)도 80건 모두 같은 오류였다. 엔드포인트가 그림을 받게 되면 같은 명령으로 바로 잰다.

결제 안전은 모델 정확도와 상관없이 **규칙으로 막는다**. 화면이 결제 수단·카드 투입·주문 확인 결제로 보이면, 확인을 받기 전에는 결제 버튼을 안내하지 않는다. 그래서 목표는 100%다.
